# Illini Market 社区整合与执行方案

版本 4 · 2026-11-12 · 当前主方案。V3 存于 revisions/v3；开发结果以 release/CURRENT_STATUS.md 为准。

Eric 希望让学生与校友在同一个产品里找到讨论、买卖闲置、了解活动，并从相关内容进入下一步。我们沿用现有 Illini Market 的账户、商品、广场、私信和举报，逐步接入 CAACI 官网已经具备的公开文章与活动能力。

本轮同时做四件事：扩大平台研究、简化并公开演示版、形成可搬到新虚拟机的 OMO 交接包、开始第一批正式社区代码。公开 demo 使用示例数据；正式代码通过独立分支检查后再进入后续发布阶段。

## 1 当前要求与执行入口

用户要求界面精美、清楚、不把所有模块拼成复杂首页，尽量减少 AI 式文案；调查更多成熟产品；把背景、接口和后续任务写到接手者能直接操作的程度；提供一个可以自行转发给合作方的 demo 网址。

- 新开发者先读 [OMO 接手入口](handoff/START_HERE.md)。
- 当前结果、部署与下一项工作见 [当前状态](release/CURRENT_STATUS.md)。
- 研究依据见 [十个平台研究](research/PLATFORM_RESEARCH.md)。
- 每批要改什么、如何验收见 [迭代清单](handoff/ITERATION_BACKLOG.md)。

本文明确方向和取舍；接口字段、测试和机器准备放到专门文件，避免一个大文档重复维护互相冲突的版本。

## 2 谁使用，以及先解决什么

| 用户与情境 | 用户要完成的事 | 首轮产品路径 |
| --- | --- | --- |
| 刚到 UIUC、准备安顿的学生 | 找可靠经验，买到所需物品，联系卖家 | 新生指南/讨论 → 商品 → 原有私信 |
| 日常在校学生 | 提具体问题，得到回应，找回有用内容 | 社区筛选/搜索 → 主题 → 回复/收藏/关注 |
| 愿意分享经验的校友 | 写清适用背景，让学生继续提问 | 校友求职板块 → 经验或提问 → 后续讨论 |
| 想参加活动的人 | 判断时间地点、来源、是否可报名 | 活动详情 → 权威报名来源；另可进入讨论 |
| 内容维护者/管理员 | 整理指南、纠正失效信息、处理举报 | 现有管理能力 → 对象上下文 → 处置/恢复/记录 |

本方案没有用竞品用户量证明这些需求已经成立。先以现有讨论和项目目标形成假设，再通过原型任务与真实小批试用验证。

## 3 五个系统怎样协同

| 模块 | 保留的职责 | 与社区的连接 |
| --- | --- | --- |
| Illini Market 二手 | 商品、价格、交易状态、私信、面交 | 帖子引用同一商品，售出/下架状态来自商品域 |
| Illini Market 社区 | 提问、经验、讨论、回复、收藏与关注 | 扩展现有广场，沿用用户、消息和治理 |
| CAACI 官网 | 官方文章、会员、家庭、活动报名、志愿者、商家目录及已有业务 | 先接公开摘要和可信链接，再按明确合同同步 |
| 活动信息 | 由主办方/来源系统维护日期、地点、报名状态 | 社区保留来源和一个主要讨论，不另造报名结果 |
| Local Pass 等商业权益 | 由实际运营系统管理供给、资格、核销、订阅 | 先定义将来所需的数据边界；确认真实系统后再接 |

两站账户暂按各自系统处理。以后用户可以主动关联两端身份，但相同邮箱不能自动授予会员、管理员或商业权益。官网会籍、华协币、商业订阅和免费社区账户分开说明。

## 4 本轮调研如何改变设计

本轮比较 Discourse、V2EX、Stack Overflow、Craigslist、Carousell、Luma、Meetup、Airbnb、Linear 和 GitHub Discussions；详细证据、限制和来源在研究报告。原对话的一亩三分地与美卡论坛作为已有背景继续保留，本次不把它们当唯一模板。

| 设计问题 | 本轮取舍 | 如何验证 |
| --- | --- | --- |
| 首页像模块拼盘 | 首屏直接展示讨论；指南与下一项活动作为辅助 | 用户能直接找到主题，不需要先理解所有组织与系统 |
| 所有内容都是同样的大卡片 | 讨论用主题行、商品用图和价、活动用时间地点 | 各类页面能快速回答用户的不同问题 |
| 入口重复、未来功能抢注意力 | 稳定五项导航；隐藏未接通的商业入口 | 同一屏无重复主入口，所有可见主动作有明确结果 |
| 信任含义混乱 | 身份、贡献、交易评价、会籍与付费资格分开 | 用户不会把“活跃”理解为“交易保证” |
| 文案像产品宣传稿 | 页面名和按钮直接说任务，示例帖子写具体问题 | 逐条删除无法帮助用户决定或行动的句子 |
| 功能增加后越来越杂 | 新功能先确定归属页面、内容供给和失败状态 | 未满足条件不新增一级导航 |

这些是本项目建议，不声称竞品模式能直接带来增长或所有样式已经获得 Eric 认可。

## 5 信息架构

主导航采用“社区、二手、活动、消息、我的”。桌面与手机保持同样的目的地；旧原型 home/community 路径保留兼容，避免断链。

社区内部保留五个话题：校园生活、二手与安顿、校友求职、活动搭子、本地优惠。它们回答“讨论什么”。提问、经验、讨论、公告等内容类型回答“作者要做什么”，属于后续可增量引入的维度；首批不强迫用户选择复杂分类树。

- 社区：搜索、板块、最近更新/待回答/精选/关注、主题列表，一个发布主按钮。
- 二手：商品图片、价格、状态、地点范围与筛选；进入详情后联系卖家。
- 活动：按日期组织，先展示时间、地点、主办来源及报名状态；进入同一活动的讨论。
- 消息：复用原有对话，不增加一个新的论坛聊天系统。
- 我的：自己的内容、收藏、关注、账户与举报进度；只显示有证据的身份/资格。
- 指南和官方文章：从相关页面进入，不再单独占一个高频主导航位。

页面的首屏内容、二级动作、文案和视觉细则见 [页面规范](handoff/DESIGN_AND_CONTENT.md)。

## 6 五条必须走通的流程

1. 用户读安顿帖，打开所引用的商品，进入原有私信；卖家标记售出后，帖子卡片与商品页一致。
2. 用户写标题、选板块、写正文并关联本人在售商品；发布失败时保留草稿，关联部分失败时能恢复且不重复发帖。
3. 用户从活动页进入唯一讨论；点击报名进入权威来源，社区没有回执时不显示已报名。
4. 校友写经验，学生提出具体问题，作者收到正确的回复通知；取消关注后不继续收到新提醒。
5. 用户举报内容，管理员查看上下文并处置，用户能看到进度；隐藏/删除后列表、搜索和分享不泄露内容，恢复有记录。

原型验证这些流程的交互。正式实现还要验证真实权限、数据写入、账号切换、错误恢复和来源变化；两者不能互相替代。

## 7 已核对的工程事实

Illini Market 当前远端 main 为 `7b18f2052e52a4268c25407d0584748477cbf978`。本轮正式站版本标识也返回该提交，但没有据此宣称所有用户流程已复验。它已有广场、评论、最多 3 件本人商品关联、私信、举报/申诉、通知和管理员能力。

原 Mac 工作目录另有登录恢复、换号和消息相关未提交改动。本轮正式社区工作使用独立副本，旧改动不被覆盖或自动合并。

## 8 接口怎样预留

接口预留通过明确对象归属和合同完成，不在页面放一排无法使用的按钮，也不提前部署无真实调用方的空服务。

| 对象 | 必须先定义的约定 |
| --- | --- |
| 社区主题 | 可空标题、受控板块、旧动态兼容、作者权限、审核与搜索范围 |
| 商品引用 | 复用现有ID与本人在售规则，状态从商品域读取，处理下架/售出/不可见 |
| 官网文章 | 来源系统+稳定ID去重，公开摘要，原文链接，编辑与撤回传播 |
| 活动 | UTC时间和显示时区、来源状态、唯一讨论、报名URL、未知/取消/结束分开 |
| 身份关联 | 用户主动证明两端身份，可撤销，不共享密码或管理员身份 |
| 商业资格 | 来源方服务端验证、有效期、撤销、unknown状态，浏览器不授予资格 |
| 通知 | 稳定事件ID与接收人去重、取消关注、删除后重新检查可见性 |

每个合同还必须定义超时、重复请求、部分成功、乱序事件、来源删除和缓存过期的处理。已有接口与候选接口分开列在 [集成合同](handoff/INTEGRATION_CONTRACTS.md)；候选路径不能被接手者当成线上已存在的路由。

| 批次 | 本批产出 | 完成标准 |
| --- | --- | --- |
| P0 研究与演示 | 研究、改版demo、公开链接、可搬走交接包 | 普通访客能打开，五条示例流程与手机桌面检查有记录 |

| P2 社区基础 | 标题/板块、发布/列表/详情、旧动态兼容 | 满足迭代清单 P2 的数据库、双账号、错误恢复、旧客户端及手机/桌面浏览器验收；仅编码、构建或部分测试通过不算整批完成 |
| P3 关注与治理 | 收藏、关注通知、举报处理、图片路径 | 权限、重复/迟到事件、删除/恢复和取消关注有证据 |

| P5 真实内测 | 真实内容、明确承接人员、小批任务测试 | 真人完成记录，关键问题修复与可回退发布 |
| P6 基于证据调整 | 一轮一至两个明确问题 | 修改与用户结果对应，不用新模块掩盖内容缺口 |
| P7/P8 后续能力 | 身份/权益，以及独立AI或票务提案 | 实际供给、协议、权限和责任满足后分别实施 |

主任务ID只有 P0–P8；研究中的观察映射用于说明依据，不建立第二套执行清单。每批的输入、具体动作、失败检查和回退见 [迭代清单](handoff/ITERATION_BACKLOG.md)。当前分支/PR/发布状态见 [当前状态](release/CURRENT_STATUS.md)。

## 10 内容、运营与真实验证

先准备能被维护的指南、真实商品、授权校友经验和可核对活动。开发者可以整理材料，但真实发布、回复、审核和申诉必须有实际承接者；不自动把所有工作指派给 Eric 或合作方。

初次主持测试建议约 5–8 名代表用户分别完成具体任务，记录误解、停顿、误点和未完成原因。人数只是本项目起步建议，不代表统计证明。之后再按内容与治理承接能力扩大邀请。

指标只记录真实行为：求助获得真人回复、有效买卖对话、活动信息准确率、举报处理时间和满观察期后的留存。点击报名不算报名成功，点击聊天不算成交，演示用户与AI代演不计入活跃或增长。

## 11 发布、费用与后续未知

公开 demo 使用独立站点，发布清单只包含示例页面、脚本、样式和必需素材。背景材料、原对话、私聊截图、配置和日志不公开。正式平台发布使用现有工程的检查与环境边界，不能把静态demo的成功当成生产发布验收。

本方案不执行历史价格、活动预算或票务合作承诺。Local Pass 的实际系统、商家供给、资格和退款核销合同确认后另开小批次；官网已经存在的会费/支付流程不因此被重写。站内AI与自有售票也分别证明需求和验收方法后再实施。

遇到方案没覆盖的小型可逆实现选择，开发者应按现有规范作出判断并记录理由；遇到身份权限、对外承诺或真实数据范围不清的事项，完成不依赖它的工作后再提出具体问题。
