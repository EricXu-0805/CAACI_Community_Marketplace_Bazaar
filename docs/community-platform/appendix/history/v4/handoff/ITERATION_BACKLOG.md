# 可执行迭代清单

更新：2026-11-12。本表按依赖排序，不承诺未经测量的总工期。实际完成状态以 `../release/CURRENT_STATUS.md` 为准；本文定义任务和验收。

## 如何执行一批

主开发者从第一条未完成且依赖满足的任务开始。检查者可以并行查兼容性、权限和用户流程，不与主开发者同时写同一组文件。每批先给出能完成的用户动作，再实现、检查、展示预览、记录结果。修复失败后只重跑受影响范围；已有通过证据没有新变化时不无限重复。

更新任务记录使用：任务 ID、分支/提交、修改范围、运行命令、测试环境、通过证据、未测范围、回退方法、下一条任务。禁止只写“全部完成”“测试通过”而不给版本和环境。

## P0 — 研究、原型整理与公开评审

- 交付平台研究、V4方案、OMO交接包和独立公开 demo；当前完成状态见 release/CURRENT_STATUS.md。
- 首页改为内容列表；商品和活动各用自己的信息结构；删除重复营销入口和未来权益占位；改为自然示例内容。
- 修复草稿、焦点、存储失败和重置交互；打包合法来源素材和图标授权。
- 发布目录只允许产品静态文件及所需素材。未接入真实账号、接口、支付或邮件。
- 验收：普通未登录访客能打开 URL；手机和桌面无关键遮挡；浏览器完成五条示例流程；未来功能有明确边界。
- 交付：部署地址、资产/版本记录、测试结果、可搬走的包、GitHub独立分支。

## P1 — 正式社区的开发基线

**依赖：**读取工程基线和本轮状态，不必等待所有未来业务决定。

动作：
1. 重新读取远端 main 的提交和当前 CI；在新目录或 worktree 建立独立分支，不覆盖原目录的登录相关改动。
2. 只从项目清单安装现有版本，验证构建和最小测试；不顺手升级全部依赖。
3. 建立使用合成账号/数据的本地或隔离测试数据库，记录目标项目的非秘密标识。检查所有可写 API、存储、邮件与支付分别指向哪里。
4. 核查登录、退出、会话恢复、换号后缓存清理。把当前代码问题与环境缺失分开记录；依赖未完成时允许继续离线 UI，但不对外内测。

验收：新机器可重复启动；用户 A 退出并换为 B 后不能看到 A 的私信或缓存；报告明确哪些真实流程未测。基线保存为一个可回退的提交。

## P2 — 标题、板块与发布→列表→详情

**依赖：**P1 的可用测试环境。第一批正式用户功能，避免同时接支付或跨站账号。

具体实现：
- `posts` 增加可空标题和受控板块字段；旧帖保持可读。字段上限、默认板块和迁移写在同一批变更中。
- 沿用现有发布器、图片、评论、点赞和举报；加入标题与板块选择，保留草稿、失败提示、可恢复的提交状态。
- 沿用 `post_items` 和最多 3 件本人 active 商品规则。服务端再次校验所有权和状态；客户端提示不能取代授权。
- 更新现有广场列表与详情，显示标题、板块、回复和更新时间；提供板块筛选。标题缺失的旧动态有自然显示方式，不强制批量生成标题。
- 处理“帖子成功，商品关联失败”的部分成功：显示已存在的帖子，允许只补关联；重试不会重复创建帖子。

验收：
- A 发带商品的新帖，B 找到并回复；A 能看到结果。
- 旧动态、旧详情链接、无标题帖子仍正常；旧客户端兼容策略有测试或明确版本边界。
- 篡改商品 ID、关联他人商品、已售出后重试、重复提交、断网重试均得到正确结果。
- 删除、下架或转不可见的帖子不会继续出现在公开列表、搜索及相关引用中。
- 原二手商品和私信路径没有回退，手机与桌面浏览器均完成任务。

回退：先用功能开关回到原展示，保持新增 nullable 字段；不把破坏性删列当快速回退。

## P3 — 关注、收藏、回复通知和治理

**依赖：**P2；与 P4 的只读内容研究可以并行。

- 收藏和关注分开，用户与主题组合唯一；重复点击保持一致；收藏默认仅本人可见。
- 复用现有通知，定义“新回复”“主题更新”“审核结果”，去重并支持取消关注；不要给同一用户重复提醒自己的行为。
- 复用现有举报、申诉、审计；补齐主题置顶/精选/关闭/隐藏/恢复的服务端权限与记录。
- 实际补验 H5 图片发布与编辑路径；现有上传压缩/类型检查不能充当内容审核。审核失败或超时不能显示审核通过。
- 限流和垃圾内容规则覆盖正常生活、二手、校友岗位及中英混合，避免把所有链接或联系方式一刀切成垃圾广告。

验收：取消关注后停止后续通知；用户不能读他人收藏或管理接口；编辑/换图/重放请求仍受校验；举报处置后各入口状态一致，恢复有记录；草稿不因收藏/关注丢失。

## P4 — 官网文章与活动的只读连接

**依赖：**P1 可读测试环境；进入社区写入和通知时还依赖 P2/P3。

- 文章先对照官网已有公开 API；活动当前为官网直接读取 published events，报名 GET 本轮出现未定位 403，没有已验证的统一活动 Feed。先定义最小公开活动 Feed 合同，不重造文章、会员或报名后台。记录响应字段、分页、公开范围与错误状态。
- 第一版使用来源明确的摘要和原文/报名链接；自动同步只导入已确认公开字段。
- 建立稳定外部引用：来源系统+来源 ID 唯一；canonical URL、source_updated_at、last_checked_at、状态。
- 同一活动只有一个主要社区讨论；官网更新、删除和接口失联各有不同显示状态。取消、改期、售罄只有在上游提供权威状态后才显示；当前缺字段时显示 unknown，未发布不自动解释为取消。
- 报名按钮跳转到权威系统。点击、关注、候补、报名确认分别记录；未拿到来源回执不显示“已报名”。

验收：用 fixture 检查发布/未发布文章、重复同步、改期、取消、来源404、超时和旧活动直链；真实来源只报告实际取得的状态和接口证据。缺失状态显示 unknown，不能靠推测通过测试。不导入参会者、会员家庭资料或未公开地址；来源故障时不显示虚假的新鲜状态。

## P5 — 内容准备与真实内测

**依赖：**P2/P3 的生产发布条件，P4 以已具备的范围进入；不让未来商业接口阻塞基本社区。

- 由 Eric 确认内容与日常承接人员，开发者不替他们承诺值班。
- 准备可核对的指南、真实可联系商品、授权校友分享和有来源活动；样例数据与真实内容分开。
- 本方案建议先找约 5–8 名代表性参与者做主持任务测试，再根据实际承接能力扩大邀请；人数为测试建议，不是统计显著性或既定招募承诺。
- 任务：找一件商品并联系；发一个问题；回复一条讨论；判断活动是否可报名；报告一条失效内容。
- 记录完成/未完成、错误、停顿和反馈；不要把 AI 模拟当参与者，不把演示点击计进产品增长数据。

进入邀请前：真实登录恢复/换号、权限、图片处理、举报承接、关键通知以及回退方法都已有证据。对外邀请由用户另行授权具体对象和内容。

## P6 — 根据证据调整

- 看求助得到真人回复的比例、从讨论进入商品后的有效对话、活动信息的准确率、举报未处理时长及满观察窗口后的留存。
- 每个指标明确分子、分母和时间窗，过滤示例/机器人/重复事件。跳转不算报名，发起对话不算成交。
- 新板块只有在现有板块持续出现无法表达的内容且有人承接时才建立。新用户没找到东西时，先检查内容和命名，再讨论新增功能。
- 每轮只选择一至两个证据最强的问题修改；保留与结果无关的稳定页面。

## P7 — 外部身份与商业权益

**启动条件：**真实系统、运营主体、供给、价格与业务责任都可确认。

- 账户关联由用户主动证明两端身份，支持撤销；跨站 subject 映射不通过邮箱静默合并。
- 资格由来源服务签发/查询，具有有效期和撤销语义；浏览器不能自行授予会员或权益。
- 商家权益明确适用对象、有效期、核销条件与来源。过期、撤销、接口不可用时不继续显示“可用”。
- 支付使用可靠回执、事件幂等、乱序处理与账务核对，取消/退款和资格变更一致；正式金额与法务文本另行确认。
- 本批完成前，普通界面不出现能误导用户的购买按钮或假会员等级。

## P8 — AI 与自有售票的独立提案

只有人工流程和数据边界稳定后，再判断 AI 搜索/整理是否有明确任务和可评测收益。知识来源、访问权限、删除传播、成本、失败提示和人工接管需要单独设计。

自有票务也要独立证明需求：库存、并发、支付、退款、核销、客服和主办方授权均有负责人。没有理由仅因原型已有活动页就实现整套售票。

## 发生新情况时怎么判断

| 情况 | 执行动作 |
| --- | --- |
| 方案未覆盖的小型可逆实现选择 | 用现有规范决定，写明理由，继续工作 |
| 当前源码与本包不一致 | 以新读源码为准，记录提交和影响，更新基线 |
| 跨站数据归属或权限不明 | 完成不依赖它的工作，对具体写入/身份动作暂缓并提出单个明确问题 |
| 出现新的收费、承诺或对外沟通 | 在动作前说明具体对象、内容、金额/影响，并核对当前授权 |
| 测试失败 | 复现、缩小范围、修复、重验受影响流程，不把失败隐藏在“后续优化” |
| 任务开始膨胀 | 拆出下一批，当前批继续完成已定义用户动作 |
