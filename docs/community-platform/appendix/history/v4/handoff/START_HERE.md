# OMO / 新虚拟机接手入口

版本：4 · 2026-11-12 · 本包维护者：Eric 当前协作的 AI 开发者。

本包让没有读过原聊天的开发者理解项目并接着执行。阅读顺序、当前结果和下一批任务以本文件为入口。`revisions/v3` 是历史；旧文档的日期和状态不能覆盖本包更新。

## 项目一句话

Eric 希望把现有 Illini Market 的二手交易和广场，逐步扩展成 UIUC 华人学生与校友使用的社区；连接 CAACI 官网的文章和活动，再为独立会员及商业权益系统预留可靠接口。

本轮用户明确要求：研究更多成熟平台；界面精美、清楚、不堆模块、尽量减少 AI 式文案；详细记录背景和接口；开始迭代；提供他可以转发给合作方的公开 demo。用户将让 OMO 在另一台虚拟机继续开发。用户允许在有权限的 GitHub 工程中开展工作。

## 三种东西必须区分

1. `prototype/` 是可分享的静态产品演示，使用本地示例数据。它不是生产社区客户端，浏览器本地存储也不是生产数据库。
2. Illini Market 正式工程仍采用自己的技术栈与账户、商品、私信、举报逻辑。正式功能应在该工程中增量实现。
3. CAACI 官网是另一套已有系统。源码已实现文章、会员、活动报名等路径，运行验收范围见工程基线证据表；不能因为社区尚未接入就重新建一套或声称尚不存在。

原型可以确定信息顺序、页面和交互，但不能证明生产权限、支付、邮件或真实使用已经通过。

## 接手后的第一条执行指令

读 `../release/CURRENT_STATUS.md` 中的 `next_task_id`，再到 `ITERATION_BACKLOG.md` 查看该任务定义。核对状态文件记录的已有分支、提交、PR与当前未提交改动，优先检出或跟踪该分支，保留已完成代码和证据；不要从最新 main 另开一份 P2 重做。只有确认没有应续接的分支，或进入明确的新批次，才建立新的独立分支。P1/P2 的编码、编译或部分测试进展不等于完整验收；按状态文件继续补环境、双账号与浏览器等实际缺口，完成条件仍以迭代清单为准。

不要一口气执行全部清单。每批写明：本次用户动作、修改范围、验证环境、结果和遗留问题。完成一个能检查的结果后，再按依赖进入下一批。

## 接手时的工作边界

- 用户已授权研究、方案、demo 迭代和开展 GitHub 开发；无需把每个可逆内部改动再次变成审批问题。
- 公开 demo 仅发布示例界面和运行必需的素材。原聊天、截图、合作谈判、身份资料、凭据和内部日志不随 demo 发布。
- 现有网站的真实用户数据、会员、报名和收款属于运行中的业务。不要把 demo 发布指令解释为任意写入这些数据的授权。
- 官网的 preview 名称及 Stripe test 配置都不能证明数据库隔离。先阅读工程基线，确认实际 Supabase 项目和服务端写入目标，再使用可写测试环境。
- 不复制 Mac 的登录状态、环境文件、令牌或浏览器配置到虚拟机。通过当前工具的正规登录方式重新获得所需权限。
- 不替用户发送合作方消息、邀约或会员邮件；本轮用户要的是可转发网址。
- 不覆盖原目录未提交工作，不直接修改默认分支，不把别人的在途改动整包带入当前批次。

## 本包的证据等级

- 用户要求：本轮直接指令和原对话中可见的明确确认。
- 源码事实：实际读取的工程文件与对应提交；部署可能与源码不同。
- 公开产品观察：注明访问日期及官方 URL，只能说明所观察的页面或文档。
- 设计/接口建议：待在项目中实现或验证，不能写成竞品证明有效或用户已经认可。
- 验收结果：区分静态检查、状态测试、真实浏览器、测试后端、线上与真人试用。

把新发现追加到 `../release/CURRENT_STATUS.md` 的变更记录；涉及产品范围的新决定同步更新对应文档，不让旧结论继续作为当前入口。
