OMO 在另一台虚拟机的执行手册

更新：2026-11-12。这里提供可重复启动的方法；具体分支、提交、公开 demo 和 PR 见 ../release/CURRENT_STATUS.md。本机绝对路径仅出现在历史证据中，不是运行依赖。

1 取得材料

优先从状态文件记录的 GitHub 分支取得 docs/community-platform/；也可以解压用户收到的交接包。两者都应包含 PLAN、handoff、research、prototype、release，且文件之间使用相对路径。

私有仓库：https://github.com/EricXu-0805/CAACI_Community_Marketplace_Bazaar.git。

使用虚拟机自己的 GitHub 登录/连接权限。不要把 Mac 上的令牌、浏览器配置、.env、会话 cookie 或完整家目录打包过去。拿到包后先读 handoff/START_HERE.md，再读状态文件；分支可能比打包时更新。

2 独立运行演示

原型是静态文件，不需要真实账户或数据库。系统需有现代浏览器；本地 HTTP 预览可用 Python 3，状态检查需要 Node。

在本包根目录执行：

node prototype/verify.js
python3 -m http.server 8769 --bind 127.0.0.1

用虚拟机内部浏览器打开 http://127.0.0.1:8769/prototype/index.html。远程主机的 localhost 不是你自己的电脑；需要观看时使用该虚拟机已有的安全预览方式，或打开已经发布的 demo，不要随手把整个交接包目录暴露到公网。

也可以直接打开 prototype/index.html 查看页面。不同浏览器、file地址和HTTP地址不共享示例存储；因此演示记录不同不等于数据丢失。

原型没有联网 API。发布/回复/举报只保存到该浏览器，重置只恢复该浏览器的示例状态。素材说明和授权在 prototype 中；不要将照片描述为真实卖家的物品实拍。

3 正式工程启动前

  1. 读取仓库自身的 AGENTS、贡献说明和 package 清单，以当前文件确定 Node/npm 版本。本轮基线记录根工程 Node 22.x、npm 10.8.2，接手时核对有没有变化。
  2. 用 git status --short 看未提交内容，用 git rev-parse HEAD 记版本；不要在不明改动上直接重置或强推。
  3. 优先续接 CURRENT_STATUS.md 记录的已有分支和提交：本地已有则切换到该分支，只有远端分支则建立其本地跟踪分支。核对远端 main 的变化，但不要因此从 main 重开 P2、丢掉已完成工作。只有确认没有应续接的分支，或进入明确的新批次，才按当时基线新建独立分支。原 Mac 上的未提交登录改动不会自动出现在 VM，既不能假定已经合并，也不能默认可丢弃。
  4. 按工程清单安装依赖，使用锁文件；不为跑通 demo 就重装整套框架或升级所有包。
  5. 先完成只读检查和不联网测试，再检查环境配置的目标。报告项目标识/域名即可，不输出秘密值。

建议命令框架：

git status --short
git rev-parse HEAD
git fetch origin
git branch --all
node --version
npm --version

以上先核对状态，不自动创建分支。之后按状态文件中的实际分支名检出已有工作；分支缺失或版本不符时先查清，不用另起同名任务掩盖缺失。现有 package 脚本和依赖安装位置以 ENGINEERING_BASELINE.md 及当前续接源码为准。P1/P2 的未完成验收继续保留，不能因分支可编译就推进到已完成或真实内测。

4 环境与接口检查表

项目 接手者应确认什么 不该做什么
GitHub 哪个账号有哪个仓库的读/写权限 把整个组织的管理员权限当作本任务必需
社区数据库 是否为本地/隔离测试项目，种子是否全为合成数据 向真实用户表插测试数据
官网数据库 当前官网配置是否仍共用 live 数据 因 preview 或 Stripe test 字样就认定可随意写
邮件/通知 本批是否禁用外发，收件人是否可控 触发真实会员邮件或保护中的历史 cron
支付 是否是明确的测试模式和测试数据 以真实卡/真实金额验证 demo
存储 测试图片桶、访问权限及清理策略 把私人图片转为公开
发布 新 demo 项目还是现有正式项目 把新原型覆盖到正式主域名

不要把“没有环境变量”自动解决为“复制生产环境变量”。若缺少测试环境，先开发可用 mock/只读适配层，并明确等待的具体配置。

5 每批检查顺序

  1. 运行直接相关的静态/类型/状态测试。
  2. 真实浏览器完成本批的正常流程，观察提交后的界面结果。
  3. 验证权限、重复提交、失败恢复、删除/失效、空结果和换账号等受影响边界。
  4. 检查手机和桌面，保存可读截图；截图不是点击测试的替代品。
  5. 查看实际提交对应的 CI/预览结果；不要用上一提交的绿色检查代表新版本。
  6. 在状态文件记录未测设备、后端或真实用户范围，然后交付分支/PR和预览。

6 公开 demo 发布

公开范围仅为 prototype 的运行文件和所需资产，发布清单见 release/PUBLISH_MANIFEST.json（若尚未生成，先生成再部署）。发布前检查包中没有原聊天、截图、内部日志、.env 或真实用户数据。

演示需要独立网址。部署完成后以未登录访客验证首页及一条核心路径，不能仅凭平台返回 READY 就宣称可分享。若启用了访问保护，先核对它是否符合用户要求；不要给对方一条只能开发者打开的链接。

保存：项目ID、部署ID、别名、Git提交或资产摘要、发布时间和访问结果。稳定别名指向新版本后，保留上一部署地址供回退。移除 demo 的权限或停止服务必须再按用户当时要求处理，不自动销毁已分享链接。

7 浏览器异常时

旧一轮预览在原生确认框后出现全局点击不响应。原型已改成页面内确认；这次异常不能写成生产发帖失败。遇到类似情况，先判断是否只有一个功能失败，还是连普通链接也无法点击；查当前页面和错误，再修对应问题。

不要在真实浏览器测试未完成时，把 Node 的页面替身检查当作等效证据。也不要为了测试去绕过验证、降低生产安全设置或操作用户无关页面。
