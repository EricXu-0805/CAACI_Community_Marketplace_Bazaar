## 聊天修复

同一个逻辑消息的第一次请求可能已写入数据库，只是响应在途中丢失。重试时，重复内容/限流触发器会先于主键唯一性检查执行。旧代码只把主键冲突和不明确的网络错误送进恢复查询，遇到 `P0001 duplicate_message` 会把已发送的消息当作未发送。

现在显式的同 ID 重试都会按 **消息 ID、发送者、会话** 查询，并核对内容与类型；读取不到时保留“结果未知”，等待后续历史记录确认。普通首次发送的明确拒绝仍保持未提交。测试使用真实的提交状态分类器，覆盖重复/限流、原消息存在、恢复不可用、内容不符和首次发送。

混合测试里 6 条消息均只写入一次，双方能读到完整历史，第三个账号读不到。实时回调不足 6 次的失败记录保留；这是继续保留客户端历史补查的重要证据，不能宣称 WebSocket 保证逐条送达。实测脚本调用真实 Auth/REST/Storage，不包含微信运行时、AI 审核接口或 Vercel 上的完整客户端请求链。

## 生产恢复方法与实际发现

使用官方 CLI 的 linked dump 获取实际生产 schema 和 data（含 public、auth、storage、private、moderation_private、extensions、realtime、迁移账本等）。两次逻辑 dump 是独立快照，不是同一次物理备份；未改生产业务行或应用权限。

恢复目标是本机 `supabase/postgres:17.6.1.104` 临时容器，网络为 `none`、没有映射端口、后台 cron 关闭。所有生产数据文件仅在本机受限临时目录，不提交仓库。只读核对结果：

- 84 个 COPY 段全部恢复，3,477 行按列输出并排序后内容哈希一致，空表正确计算为零行。
- 对照同一 schema 创建的空模板，表权限/所有者、RLS、策略、约束及其有效状态、函数权限/定义完全一致。
- auth.users 16、public.items 14、public.messages 25、storage.objects 22；这里是全表备份数量，不是公开可见数量。

**发现：不能把整份 schema 先恢复后直接灌数据。** 历史 `device_fingerprints_fp_hash_sha256_chk` 是 NOT VALID 约束，已有旧数据不满足新格式；NOT VALID 仍会检查新灌入的行，导致该恢复顺序失败。正确顺序是 **pre-data → data → post-data**，最后重新建立索引、外键、触发器和原有 NOT VALID 约束。没有删改生产历史数据来让恢复测试变绿。

本次用空 schema 数据库生成 schema-only custom archive，以 PostgreSQL 自己的 section 划分恢复 pre-data/data/post-data，最终核对通过。数据导入阶段约 140ms，仅是一个步骤，**不是灾难恢复 RTO**。

图片必须单独备份。[Supabase 官方说明](https://supabase.com/docs/guides/platform/backups)明确数据库备份不包含 Storage 对象字节。本轮 19 个可读对象只恢复到本机文件系统并核对哈希，3 个不可用源对象保留失败记录；不能宣称完整 Storage 服务恢复。

托管后台已读到物理备份完成状态，恢复到新项目的确认页列明：数据库/索引/角色可转移，Storage、Auth 配置/API key、Edge Functions、部分扩展设置需要另行配置。确认页显示初始新增约 $0.50/月；已向负责人请求同组织临时项目及总计不超过 $5 的明确授权，尚未点击最终继续。页面估价不代替最终账单。
