## 已落实的修改

商品列表与搜索原先每读一条商品，都调用一次私有卖家权限函数。改为每条数据库语句只取一次当前不可对外展示的卖家集合；仍遵守三级封禁、开始时间、到期时间、主动解除，以及本人可查看自己未删除商品的规则。

新增函数仅位于未暴露的 `moderation_private`，固定查找路径并撤销 PUBLIC 执行权。它不提供封禁原因或其他资料；公开搜索仍为 SECURITY INVOKER，搜索词、排序、匹配算法及写入规则不变。旧的逐卖家函数继续服务其他调用方。没有跨请求缓存，解封和到期无需等待缓存刷新。

迁移 `20260914200143_statement_scoped_listing_search.sql` 已分别应用到 staging 和 production。两边商品行数与全行摘要未变化，两个搜索 RPC 定义/权限摘要未变化，匿名可见结果与复杂搜索结果摘要均与修改前一致。生产当前只有两条公开可见商品，这项现场核对不代替大数据量测试。

- 封禁的未来开始、到期、主动解除、重复记录、空 profile ID 均保持原结果。强制通用预编译计划后，跨语句解封、到期和切换账号立即生效。
- 本人插入/更新、跨账号修改/删除和所有者转移拒绝均通过；被封禁本人仍能更新自己的未删除商品。
- 三万条合成封禁记录下，查询计划显示集合函数仅执行一次；回滚后全部对照结果相同。测试数据库均已自动删除。
- staging 的真实 REST 搜索返回 200；公开 RPC 调用私有 helper 返回 404/PGRST202，直接选择私有 schema 返回 406/PGRST106。
- Supabase 安全检查的前后告警集合相同：生产原有 19 个需认证的 SECURITY DEFINER 入口告警及 21 个默认拒绝表的提示，没有新增告警；这些既有提示不能解释成“安全问题归零”。[检查说明](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable)

## 被否决的搜索改写

进一步尝试了复用重复文字评分、先筛匹配再排名、减少中间字段、预处理大小写等候选。其中复用评分在旧的高度重复合成语料上明显更快，但换成每条都有独特长描述后反而变慢，因此没有部署任何搜索 RPC 改写。

同一本机、相同 10,001 条样本规模、三次计时中位数（包含数据库客户端启动开销，不是托管 HTTP p95）：

| 语料与三词搜索 | 原实现 | 只改权限检查（本次采用） | 权限检查 + 复用评分（否决） |
|---|---:|---:|---:|
| 历史重复描述 | 450ms | 423ms | 119ms |
| 每条独特长描述 | 1,305ms | 1,299ms | 1,675ms |

这个差异揭示此前容量样本的盲点：不能只用同一段描述复制一万条商品来判断搜索性能。后续容量基准必须同时保留重复和独特长描述语料，以及最大搜索词数和无结果查询。

**复杂搜索容量仍未通过。** 本次减少了权限检查开销；没有证据表明它能单独消除上一轮托管混合负载的超时。下一轮需比较查询索引/执行方案与计算规格，保持原定 p95 2 秒标准，再完整执行通知、媒体和聊天混合负载。
