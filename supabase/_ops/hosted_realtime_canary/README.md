# Hosted Realtime staging activation unit

This directory is a **staging-only**, manually reviewed activation package for
the hosted Realtime canary. It is deliberately outside migration history and
must not be copied into `supabase/migrations`, production, normal CI, or a
shared development database.

One explicitly approved A-01 attempt entered a remote staging transaction on
2026-08-01. Its in-transaction VERIFY failed closed before COMMIT, PostgreSQL
rolled the whole transaction back, and an immediate read-only census plus a
fresh PRECHECK found zero package objects, jobs, memberships or write residue.
The repaired source in this directory has not been retried remotely. The prior
approval is consumed, the public target allowlist remains empty, and A-02 stays
blocked until a new Gate 0 and a new exact A-01 approval exist.

`LOCAL_BOOTSTRAP.sql` and `LOCAL_REGRESSION.sql` are destructive fixtures for a
brand-new disposable local PostgreSQL cluster only. They create stub Auth/cron
schemas and must never be run against Supabase or any shared database.

## What this package adds

- one server-owned environment sentinel;
- an immutable fixture-manifest digest covering A/B/C, AB/AC, lineage and
  revision;
- one database-enforced active-run lease generated by the safe launcher;
- protocol revision 2 ledgers for zero to eight base messages, one optional
  atomic 51-message scale batch with one authoritative `created_at`, one
  optional already-emailed notification, and reversible A↔B block state;
- canary-only message, notification and block mutation guards;
- exact actor/conversation/marker/quota checks. A complete success run has
  eight base messages plus the 51-message batch, but cleanup also accepts a
  safely ledgered partial run after an interrupted request;
- exact three-resource cleanup, conversation timestamp restoration,
  seller-response and profile-timestamp baseline verification, and a
  no-archive invariant;
- a five-minute database TTL recovery job;
- fail-closed Auth-session observation for the three disposable accounts;
- two postgres-owned, private `SECURITY DEFINER` Auth adapters that return only
  validated synthetic request context or a three-actor session count; the
  NOLOGIN executor receives no `auth` schema or managed-table access;
- a mandatory read-only check of the exact managed `realtime.messages`
  owner/RLS/policy/grant catalog before activation;
- read-only PRECHECK/VERIFY, an explicit RECOVER operation, and a fail-closed
  ROLLBACK.

The activation role and every function are staging-only. API roles receive no
package-table access. `environment()` is the only anonymous RPC; `begin_run`,
`insert_message`, `insert_scale_batch`, `insert_notification`, `set_block`,
`cleanup`, and `cleanup_v2` are authenticated RPCs with fixed signatures.
The v1 cleanup remains fail-closed once a scale ledger exists; protocol-v2
runs use `cleanup_v2`.
Each activation is one-shot: cleanup closes write admission before deleting
rows. The final anonymous sentinel can still prove zero residue, but another
run requires clean rollback, a fresh PRECHECK/provider proof, and a new
activation review.

Hosted Supabase owns the `auth` schema with a managed role. The ordinary
`postgres` operator can read the required Auth catalog but cannot delegate
schema `USAGE`, so activation must not grant `auth` access to the executor. The
two private Auth adapters remain owned by `postgres`, fix `search_path` to
`pg_catalog`, revoke API/PUBLIC execution, and expose no email, metadata, JWT,
token, identity row, or session list. All other package functions remain owned
by the NOLOGIN executor and can reach managed Auth only through those adapters.
The session-count adapter is bound by a SHA-256 digest in its function
configuration to the exact A/B/C IDs and dataset lineage, and VERIFY pins that
configuration to the server-owned environment record. It also revalidates the
three role markers, synthetic metadata, `.invalid` email shape and email-only
identities before counting. Arbitrary distinct user IDs therefore cannot turn
it into an Auth-session oracle.

## Inputs

The SQL files use `psql` variables. These values are public identifiers, not
credentials:

```text
project_ref
dataset_lineage
fixture_manifest_sha256
sentinel_id
fixture_revision
actor_a_id
actor_b_id
actor_c_id
conversation_ab_id
conversation_ac_id
provider_disable_proof_sha256
provider_proof_expires_at
max_access_token_lifetime_seconds
approval_reference
```

`STAGING_PREREQ_enable_pg_cron.sql` consumes the same fixture-binding inputs
and additionally requires `prerequisite_mode` to be exactly
`apply-approved-staging-pg-cron`. The other accepted value,
`local-guard-only`, is hard-bound to the isolated Unix-socket regression
database and always rolls back; it cannot be used on Supabase.

The provider proof is the SHA-256 digest of a separately reviewed, short-lived
control-plane record. That record must prove the exact Supabase project has no
production data, no provider/webhook/email side effects for these fixtures,
exactly three accounts bound to the canary roles are disposable password-only
accounts, every other synthetic account is separately reviewed and isolated,
and the configured access-token lifetime is no greater than the supplied
bound. A Boolean written by this SQL cannot prove external Auth, SMTP, OAuth,
Vercel, Dashboard configuration, or that a database identity is the intended
environment by itself.

The known 2026-08-12 staging snapshot contains four users/profiles: A/B/C plus
one protected-smoke synthetic nonparticipant, together with 20 sessions, 20
refresh tokens and 20 device-fingerprint rows in the global census. These are
snapshot facts, not a reusable baseline. The fourth account must not be
deleted or silently relabeled. A fresh Gate 0 must list its purpose and
commitment, prove it is absent from AB/AC membership, canary-role metadata,
marker writes and launcher credentials, and repeat the global
session/refresh/fingerprint census. `PRECHECK.sql` validates only the supplied
A/B/C fixture boundary and therefore is not evidence that the whole project
contains exactly three identities.

The same exact proof digest and expiry must be copied into the separately
reviewed source-controlled hosted target. The anonymous environment sentinel
returns both values and the harness compares them before sending any password;
the database Boolean alone is never accepted as proof.

The proof must still be valid for at least one hour and at most 24 hours when
activation runs. The activation itself expires after 72 hours. Refreshing or
changing the proof requires rollback and a new review.

### Producing the provider proof

The 2026-08-01 attempt stalled here: the contract above says what the proof must
establish but not what to write down, so there was nothing to hash and nothing
for a second person to check. The record is therefore fixed in shape.

Write exactly these lines to a file, UTF-8, LF endings, one trailing newline,
no other content. Every `<>` is replaced by an observed value, never by a guess:

```text
caaci-hosted-canary-provider-proof-v1
observed_at: <UTC ISO-8601, when the checks below were performed>
expires_at: <UTC ISO-8601, at least 1h and at most 24h after activation will run>
project_ref: <20-char staging ref>
project_name: <exact name shown in the Supabase dashboard>
no_production_data: <yes|no> — <what was counted, and where>
no_provider_side_effects: <yes|no> — <SMTP/webhook/OAuth state observed>
accounts_disposable_password_only: <yes|no> — <the three account ids and their providers>
isolated_synthetic_nonparticipants: <count> — <ids, purpose/commitment and boundary evidence>
access_token_lifetime_seconds: <integer, as configured in Auth settings>
reviewer: <the person who observed all of the above>
```

Where each line is observed — none of it is visible from SQL, which is why a
database Boolean cannot stand in for it:

| line | where |
| --- | --- |
| `project_ref`, `project_name` | Supabase → Project Settings → General |
| `no_production_data` | Table editor / SQL editor: a fresh global census identifies every synthetic fixture row and proves no production data; it must not assume three profiles globally |
| `no_provider_side_effects` | Auth → Emails (custom SMTP off or pointed at a sink), Auth → Providers (no OAuth provider enabled), Database → Webhooks (none), Edge Functions (none deployed that send) |
| `accounts_disposable_password_only` | Auth → Users: exactly A/B/C carry the three canary roles, each uses only the `email` provider and no real address |
| `isolated_synthetic_nonparticipants` | Auth, profiles, conversations and the fresh census: list every other synthetic account, its protected purpose/commitment, and evidence it is not an A/B/C role, AB/AC participant, launcher credential or marker writer |
| `access_token_lifetime_seconds` | Auth → Sessions → Access token (JWT) expiry. `ACTIVATE.sql` rejects anything outside 300–3600 |

Then:

```sh
shasum -a 256 provider-proof.txt      # -> provider_disable_proof_sha256
```

`ACTIVATE.sql` only sees that digest and the expiry, so the digest is worth
exactly as much as the review behind it. An executor who writes the record and
also runs the activation has proved nothing to anyone.

The same digest and `expires_at` are later copied verbatim into
`app/e2e/hosted/approved-targets.ts` (step 7). The anonymous sentinel returns
both and the harness compares them before any password is sent.

`approval_reference` is a separate 8–200 character string with no control
characters. It must name what was approved, so that a later reader can tell
which review a row came from — for example
`A-01 <project_ref> proof <first 12 hex of digest> manifest <first 12 hex of manifest> approved <UTC date> by Guoyi (Eric) Xu`.

`fixture_manifest_sha256` is not an independent assertion: `ACTIVATE.sql`
recomputes it from `project_ref`, `dataset_lineage`, the sentinel id, the
revision and the five UUIDs, and raises `activation_fixture_manifest_mismatch`
on any disagreement. A wrong value fails closed, so it can simply be computed:

```sh
python3 - <<'EOF'
import hashlib
fields = [
  'caaci-hosted-fixture-v1', '<project_ref>', '<dataset_lineage>',
  '<sentinel_id>', '<fixture_revision>',
  'member-a', '<actor_a_id>', 'member-b', '<actor_b_id>', 'member-c', '<actor_c_id>',
  'ab', '<conversation_ab_id>', 'ac', '<conversation_ac_id>',
]
print(hashlib.sha256('\x1f'.join(fields).encode()).hexdigest())
EOF
```

## Hosted operator contract and local evidence

This package intentionally targets PostgreSQL 16 or newer and a real hosted
`postgres` operator that is LOGIN + CREATEROLE but not superuser. PostgreSQL 16
creates one automatic, non-inherited ADMIN membership when that operator
creates the dedicated executor. Activation adds a separate non-inherited
`SET` membership. The operator must therefore be a member of the executor but
must not inherit its privileges; every executor-owned operation uses an
explicit transaction-local role switch and returns to `postgres` afterward.

The executor is NOLOGIN, NOINHERIT, non-superuser, and cannot create roles,
databases, or bypass RLS. Temporary `CREATE` on the public/private schemas is
used only for ownership transfer and is revoked before activation commits.
VERIFY, RECOVER, and ROLLBACK all reject unexpected role edges or inherited
executor access.

The hosted `postgres` operator may separately inherit trusted platform access,
such as `pg_read_all_data`. VERIFY does not mistake that pre-existing operator
baseline for an inherited executor grant. Instead, it compares each private
package table's ACL with the exact default ACL of its NOLOGIN owner in both
directions and rejects every explicit column ACL. A direct grant to `postgres`,
an API role, PUBLIC, or any other grantee therefore still fails closed.
Effective API and managed-Auth checks derive the complete table-privilege
vocabulary from PostgreSQL's catalog, so PostgreSQL 17 `MAINTAIN` is included
without hard-coding a server-version list.

`LOCAL_REGRESSION.sql` has been exercised from separate PostgreSQL 16 and 17
connections whose actual session user is a non-superuser `postgres` with
CREATEROLE and inherited `pg_read_all_data`. This simulates the hosted failure's
relevant inherited platform-read topology without claiming every hosted role
edge is locally identical. The regression proves that direct table and column
package grants are rejected even though the operator already has effective
read access. On PostgreSQL 17 it additionally grants `authenticated` inherited
`pg_maintain` inside a rolled-back negative test and proves effective
`MAINTAIN` is rejected.

The final frozen protocol-v2 source manifest
`e3adaa806b35270cee7e9b76da3e5c2838046eaafb8d333f3a342bbe86b85490`
passes the complete isolated chain on PostgreSQL 16 and 17. Both versions cover
the prerequisite's exact target-binding guard and a known-production negative,
canonical managed-Realtime verification, base-eight writes, the atomic
51-message timestamp tie, the exact notification marker, both block/unblock
journeys, safe partial cleanup, normal cleanup, abnormal lease expiry,
recovery, standalone verification and rollback with final residue zero. They
also prove fail-closed negative gates for extra public grants/functions/
policies, malformed cleaned-history ledger timing/block state, and persisted
run-counter drift. The local cron catalog is still a stub and its heartbeat is
invoked manually. These passes therefore prove the local SQL and permission
model only; they do not prove the real pg_cron worker, a hosted heartbeat, or
any staging/production readiness.

From `app/`, `npm run smoke:hosted-realtime-sql-local` reproduces this evidence
in a fresh isolated PostgreSQL 16.x or 17.x cluster, selected by the `initdb`
first on `PATH`. The runner accepts no database URL or credential, disables TCP
listening, uses a bootstrap superuser only to initialize the isolated cluster,
roles and database, and runs the regression through a separate LOGIN +
CREATEROLE + NOSUPERUSER role named `postgres`. It verifies the fresh database
owner and role settings before destructive bootstrap, prints a source-manifest
SHA-256, verifies rollback residue, and removes only its guarded `/private/tmp`
cluster on exit. For runs that reach SQL execution, the complete synthetic
regression transcript remains in the unique `/private/tmp` evidence log printed
on success or failure; it contains no hosted credential.

## Required order

0. Establish Gate 0 outside SQL: independently confirm the exact Supabase
   project ref and connection, provider proof, fixture manifest and synthetic
   census. PostgreSQL has no trusted built-in Supabase project-ref value, so
   no SQL assertion can replace that connection review. If `pg_cron` is
   absent, run `STAGING_PREREQ_enable_pg_cron.sql` with the same exact
   fixture-binding inputs and
   `prerequisite_mode=apply-approved-staging-pg-cron`. Its first database
   action is the repository's read-only managed-Realtime verifier. In the
   following single transaction it rejects the known production ref, binds
   the supplied ref and manifest to the database-resident A/B/C metadata and
   AB/AC relationships, then and only then runs the DDL. Any failed guard or
   postcondition rolls the transaction back. If `pg_cron` or the `cron` schema
   already exists, the prerequisite fails loudly; do not treat that failure as
   installation evidence. This file remains outside migration history —
   production has no pg_cron extension and must not acquire one.
1. Independently verify the immutable Preview, exact project, fixture manifest,
   provider proof, the three canary-role accounts, both conversations, and the
   separately reviewed isolated synthetic-nonparticipant census. The current
   known fourth protected-smoke account is allowed only under that explicit
   boundary; it is not a canary actor and must not be deleted.
2. Before activation, repeat the read-only database gates. Run the
   repository-level
   `../VERIFY_20260719164126_reconcile_managed_realtime_authorization_contract.sql`
   to pin the exact managed `realtime.messages` owner, RLS policies, predicate,
   dependency grants, and ACL provenance; then run this directory's
   `PRECHECK.sql` with all variables.
3. Review both outputs, including the actual hosted operator role/capabilities
   and cron surface. Any unknown policy or trigger, missing required privilege,
   existing conversation archive, active Auth session, fixture drift, or
   residue is a stop. A disposable local superuser pass is not hosted
   capability evidence.
4. Stop again for Eric's explicit approval of the exact staging project,
   provider proof, inputs, and bounded synthetic writes: at most eight base
   messages, one atomic batch of exactly 51 messages, one notification and
   reversible A↔B block transitions. Only then run `ACTIVATE.sql`. It repeats
   the read-only gates, takes row/advisory locks, installs the package,
   schedules TTL, and executes zero-residue postconditions before commit.
5. Wait for the first real five-minute cron execution, then run `VERIFY.sql`
   independently. The in-transaction verification inside `ACTIVATE.sql`
   deliberately does not count as heartbeat evidence; standalone `VERIFY.sql`
   fails until a recent server-owned heartbeat exists. Also retain a read-only
   `cron.job_run_details` row from after activation whose job ID, command,
   database and `username=postgres` match the installed job and whose status is
   `succeeded`. A fresh heartbeat alone is insufficient worker attribution
   because the operator can invoke the TTL function manually.
6. Independently review activation, heartbeat, zero-residue, anonymous
   `lifecycle_state=ready`, and the exact provider proof returned by the
   sentinel.
7. Only after that review and a second explicit approval may the exact target
   record be added to `app/e2e/hosted/approved-targets.ts`.

No service-role, management, provider, deployment or admin credential is ever
passed to the Playwright launcher.

## Normal and abnormal cleanup

The launcher creates `CAACI_HOSTED_CANARY_RUN_ID`; a non-empty parent value is
rejected. After anonymous preflight it logs in only SDK actor A and atomically
obtains the database lease. B/C and browser logins occur only after that lease.

Normal cleanup sends the complete sorted local message-attempt set and the
optional notification ID set to `cleanup_v2`. The server accepts zero to eight
ledgered base messages, an optional all-or-nothing 51-message scale ledger, an
optional notification ledger and any legal applied block prefix. It deletes
only exact ledger/public intersections, restores any still-active canary block,
restores/validates derived state, and returns live **database** residue. This
partial-run support exists only so an interrupted request can be cleaned
safely; the client/reporter still requires all eight base messages, all 51
scale messages, the notification, and both block/unblock journeys before a
canary run is green.

The harness then revokes every exact browser and SDK session through the
ordinary Auth API before it accepts the anonymous environment sentinel again.
If an attempted request never reached the database, the returned deletion
counts differ from the local attempt set: cleanup still completes when the
remaining ledger is structurally valid, but the harness remains red.

On SIGKILL, power loss or host death, the five-minute TTL job performs the same
exact three-resource ledger cleanup after the lease expires. It never
broad-deletes by marker prefix and never writes Supabase-managed
`auth.sessions`. A TTL-cleaned run is left in `recovery_required`; a malformed
message/notification ledger, illegal block transition, ledgered row alteration
or unknown derived mutation is left `quarantined`. Both states keep the
environment blocked.

`RECOVER.sql` is intentionally a separate, approved operation. It requires a
short-lived management-plane proof that all three disposable canary accounts
had their sessions globally revoked and passwords rotated, verifies their
`auth.sessions=0`, and enforces the reviewed maximum access-token lifetime plus
clock skew before it can clear `recovery_required`. It also requires every
ledgered message and notification to be absent/deleted, every block transition
to be well formed and applied, and both A↔B block rows to be absent. The
management credential and proof record stay outside this package and outside
the harness. A `quarantined` mismatch cannot be waived by `RECOVER.sql`.

## Rollback

`ROLLBACK.sql` refuses an active run, residue, quarantine, derived-state drift,
unknown package object, or mismatched project/sentinel. It closes admission,
takes the same database lock, unschedules the exact TTL job, removes only the
reviewed policies/triggers/functions/tables, revokes the executor grants and
drops the dedicated NOLOGIN role. It never uses `CASCADE`.

Rollback does not delete the three Auth users, profiles, conversations or
fixture seed data. It also never touches an isolated synthetic nonparticipant.
Those are separate administrator-owned staging fixtures.
